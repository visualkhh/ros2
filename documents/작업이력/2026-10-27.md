# 2026-10-27 — Pi 첫 세팅 · tool · 펌웨어 · 실기 첫 주행

로봇: TurtleBot3 Waffle Pi 개조 (맨 위 판 제거, LDS-03 1층 앞) · Raspberry Pi 4 4GB · Ubuntu 26.04 · ROS 2 Lyrical.
결과: Pi 세팅 완료 · tb3_wheels 펌웨어 업로드 · tb-only 실기 구동 · PC 텔레오퍼로 주행. 라이다 드라이버는 아직.

각 항목: **증상 → 원인 → 해결 → 교훈**.

## 1. Pi 첫 부팅 · 접속

### 1-1. WiFi 설정했는데 SSH가 안 붙음
- 증상: Imager로 WiFi·SSH 넣고 부팅 → 접속 불가. 모니터 없음.
- 원인: SD카드를 PC에 꽂아 로그 확인 → 첫 부팅에 `wlan0`이 아예 안 올라옴. `netplan-configure.service`(05:44:12)가
  cloud-init이 `/etc/netplan/50-cloud-init.yaml`을 쓰기(05:44:28) **전에** 돌아 네트워크가 구성되지 않음 (26.04 첫 부팅 순서 문제로 추정).
- 해결: **한 번 더 재부팅** → 정상 연결.
- 교훈: 모니터 없이 쓸 땐 첫 부팅 후 3분 기다렸다 재부팅. 안 되면 SD카드 `writable/var/log`(journal·cloud-init.log)를 PC에서 읽는다.

### 1-2. `ssh pak@pak.local` → `Could not resolve hostname`
- 원인: 첫 부팅에 인터넷이 없어 cloud-init의 `avahi-daemon` 설치 실패 → mDNS 없음.
- 해결: `nmap -p22 --open 10.2.12.0/24` + SSH 배너·MAC(`2c:cf:67` = Raspberry Pi)으로 IP 찾아 접속 → `apt install avahi-daemon`.
- 교훈: `.local` 실패 ≠ WiFi 실패. [SSH 문서 7장](../raspberry/ssh-pak-local-troubleshooting.md).

### 1-3. `ssh-copy-id 10.2.12.198` → 비번 맞는데 `Permission denied`
- 원인: 사용자명 없이 IP만 → PC 사용자 `pank@`로 접속 시도.
- 해결: `ssh-copy-id pak@10.2.12.198`. 프롬프트가 `pak@…'s password:`인지 확인.

### 1-4. AI가 sudo 못 함
- 원인: Imager user-data에 `sudo: null` → 비번 요구.
- 해결: `/etc/sudoers.d/90-pak` NOPASSWD (사람이 비번 1회). [AI 접근 문서](../ai/ai-passwordless-robot-access.md).

### 1-5. `apt install` 이 40분 동안 `Could not get lock`
- 원인: 인터넷 첫 연결 시 unattended-upgrades가 패키지 120개(커널 포함)를 업그레이드 중. SD카드라 느림.
- 해결: 기다림 (중간에 끊으면 커널·libc 반쯤 설치 → 부팅 불가 위험). 끝나고 재부팅.

### 1-6. 파이 IP가 바뀜
- 10.2.12.198 → 재부팅 후 10.2.12.142 (DHCP). `~/.ssh/config`를 `HostName pak.local`로 둬서 영향 없음.

## 2. ROS 설치

### 2-1. ROS 설치가 1.1 GB · 패키지 1,576개
- 원인: `ros-lyrical-nav2-bringup`이 Gazebo(`gz-*`)·TurtleBot 시뮬레이션까지 의존. `navigation2`만 깔아도 1,201개(slam_toolbox·rviz 플러그인이 rviz/gz를 끌어옴).
- 결정: 그대로 설치 (tool이 nav2_bringup launch 파일을 씀, 디스크 여유 24 GB). Pi 다운로드 ~22 kB/s 구간이 있어 오래 걸림.

### 2-2. cartographer_ros 없음
- 원인: Lyrical apt에 `cartographer`(코어)만 있고 `cartographer_ros` 없음.
- 해결: SLAM은 **slam_toolbox**.

### 2-3. 문서가 Jetson·Lv2 과제 기준이었음
- 해결: ROS·OpenCR 문서를 Pi 4 기준으로 다시 씀 (MoveIt·RTAB-Map·YOLO·pick_ik 제거). Pi 메모리 4GB → swap 2GB, `colcon build --parallel-workers 2`.

## 3. tool · Nav2 (PC 시뮬레이션: mock_base + 가짜 라이다)

### 3-1. Nav2 경로는 나오는데 바퀴가 안 움직임
- 원인: Lyrical Nav2 기본 `cmd_vel` = **TwistStamped**, mock_base·자체 드라이버는 **Twist** → 타입 불일치로 연결 안 됨.
- 해결: `tool/config/nav2_params.yaml` 각 노드에 `enable_stamped_cmd_vel: false` (following_server는 섹션 추가).

### 3-2. `initpose`를 보냈는데 amcl이 무시
- 원인: CLI가 방금 만든 publisher가 amcl과 DDS 연결되기 전에 발행 → 유실.
- 해결: 구독자 수 > 0 될 때까지 기다린 뒤 발행 + amcl_pose 응답 확인.

### 3-3. 목표(goal)가 무시되거나 "거부됨"
- 원인 ①: 서버가 보여도 goal 서비스 연결 전 첫 요청이 사라짐 → 0.5초 대기 후 전송, 응답 없음/거부를 구분해 출력.
- 원인 ②: Nav2 주행부(bt_navigator 등)는 **초기 위치를 받아야** costmap이 `map→base_link` TF를 얻고 활성화됨. 활성화 전(약 25초+) `/goal_pose`는 조용히 버려짐.
- 교훈: 순서 = Nav 시작 → **초기 위치** → 준비 완료 후 목표. (tool에 "Nav 준비 완료" 표시 추가 예정)

## 4. 드라이버 · URDF

### 4-1. `opencr_driver`가 시작하자마자 죽음
- 원인 ①: 메서드 이름을 `handle`로 지음 → rclpy `Node.handle` 속성을 덮어씀 (`'method' object does not support the context manager protocol`). → `handle_line`.
- 원인 ②: Lyrical rclpy 로거에 `warn()` 없음 → `warning()`. (기존 RL 노드 2개도 같은 버그)
- 교훈: PC에서 가상 시리얼(socat + 가짜 OpenCR)로 먼저 돌려보면 실기 전에 잡힘.

### 4-2. 로봇이 Burger가 아니라 Waffle Pi
- 처음엔 Burger로 가정(바퀴 간격 0.160). 상품 링크로 Waffle Pi 확인 → 간격 0.287, 몸통 266mm, URDF 다시 작성.
- 라이다도 LDS-01이 아니라 **LDS-03**(2025년 10월부터 교체품) → 드라이버 `coin_d4_driver` (TurtleBot3 `LDS_MODEL=LDS-03`과 같음, apt 없음).
- 교훈: 하드웨어 모델·라이다 버전부터 확인.

### 4-3. `base_link` 루트 vs `base_footprint`
- 처음엔 `odom→base_link`. 업계 표준(REP-105, TurtleBot3)은 `odom→base_footprint→base_link` → 드라이버·URDF·mock·SLAM·amcl 모두 바꿈.

### 4-4. 라이다가 1층 앞이라 몸통이 스캔에 찍힘
- 해결: `laser_filters` Box 필터로 base_link 기준 몸통 상자 안 점 제거 (`/scan_raw` → `/scan`). Nav2는 원 대신 사각 footprint.

### 4-5. `deps.repos`의 `version: jazzy`
- 오해: ROS 배포판이 아니라 **git 브랜치 이름**. ROBOTIS에 lyrical 브랜치가 없음 → 커밋 SHA로 고정, 주석으로 설명.

## 5. OpenCR 펌웨어 (Pi arm64에서 빌드·업로드)

### 5-1. `setup.sh` 실패: armhf `404 Not Found`
- 원인: 업로더 `opencr_ld_shell_arm`이 32비트 → `libc6:armhf` 필요. Ubuntu 26.04는 arm64 = `archive.ubuntu.com`, **armhf = `ports.ubuntu.com`에만** 있음.
- 해결: 기존 저장소는 `Architectures: arm64`, armhf는 ports에서 받는 `.sources`를 setup.sh가 자동 생성.

### 5-2. 컴파일 실패: `macro "min" passed 3 arguments`
- 원인: OpenCR 코어 `wiring_constants.h`의 `min(a,b)`/`max` 매크로가 gcc 14 newlib `<map>`의 `std::min(a,b,comp)`을 깨뜨림 (DynamixelSDK가 `<map>` 포함). 스케치에서 `#undef`해도 라이브러리 .cpp에서 또 터짐.
- 해결 1차(실패): 매크로 → 템플릿으로 바꾸며 `extern "C"`를 닫았다 엶 → 헤더가 바깥 `extern "C"` 안에서 포함돼 `template with C linkage`.
- 해결: 템플릿을 **`extern "C++" { }`** 로 감쌈. setup.sh가 코어를 패치 (`tool-patch: minmax2`).

### 5-3. 기존 펌웨어는 아무것도 안 보냄
- `test-firmware` 응답 0바이트 = TurtleBot3 기본 펌웨어(질의 전엔 무송신). tb3_wheels 업로드 후 `S` 20 Hz 확인.

## 6. 실기 첫 주행

### 6-1. PC CLI에서 `odom ✗` · 텔레오퍼 안 먹힘 (ping은 됨)
- 원인: 사내 WiFi가 **멀티캐스트(DDS 자동 탐색)를 버림** → 처음엔 보였다가 끊김. Pi에서 본 `/cmd_vel` 발행자 0.
- 해결: PC 쪽 `ROS_STATIC_PEERS=pak.local`(유니캐스트) — 한쪽만 지정해도 양방향. `run-cli`·`run-rviz`가 PC에서 자동 설정. 직접 `ros2` 칠 땐 export 후 `ros2 daemon stop`.
- 2차: `pak.local`을 그대로 넘기면 시작 순간 mDNS 실패 시 `Unable to resolve peer pak.local`로 CLI가 죽음 → peers.sh가 IP로 바꿔 넘기고 실패 시 마지막 IP 사용.
- 3차: 베이스 재시작 후 다시 텔레오퍼 안 먹고 RViz 지도 안 뜸. 원인 = **STATIC_PEERS는 상대의 참가자 슬롯 0~3만 탐색**
  (Fast DDS `maxInitialPeersRange` 기본 4). Pi에 참가자 8개(포트 13660~13675) → 뒤 슬롯 드라이버·SLAM이 안 보임.
  해결: Fast DDS 프로필 `maxInitialPeersRange=32` + initialPeers=Pi IP (`tool/.run/fastdds_peers.xml`, peers.sh가 생성).
- 교훈: "처음엔 됐는데 재시작하니 안 됨" = 탐색 범위/슬롯 문제 의심. `sudo ss -ulnp`로 Pi의 DDS 포트(도메인 25: 13660+2×슬롯) 확인.

### 6-1b. SLAM 지도가 안 생김 (`/map` 없음)
- 원인 ①: 라이다 드라이버 미설치 → `/scan` 없음. `coin_d4_driver` 빌드 후에도 `lidar.yaml`이 설치 폴더에 없음(오래된 build 캐시) → `rm -rf build/tb3_bringup install/tb3_bringup` 후 재빌드.
- 원인 ②: LDS-03는 한 바퀴 점 개수가 395~404로 매번 다름 → slam_toolbox가 `LaserRangeScan contains 403 range readings, expected 404`로 스캔을 버림.
  해결: `scan_resample` 노드로 400칸 고정 (`/scan_raw → 몸통 필터 → /scan_filtered → 고정 칸 → /scan`).
- 원인 ③: 사용자가 PC CLI에서 SLAM·베이스를 시작 → PC에 떠서 `/dev/opencr` 못 찾고 지도도 PC 폴더 기준. → tool이 로봇이 아니면 시작 거부.

### 6-2. `w` → 제자리 우회전, `d` → 후진
- 1차 대응(틀림): 드라이버 방향 부호만 바꿈 (`left_dir -1`) → 직진은 맞지만 회전이 반대·odom 좌우 뒤집힘이 될 수정.
- 원인: **펌웨어 ID 매핑이 반대** — 이 로봇은 **ID 1 = 오른쪽, ID 2 = 왼쪽**인데 펌웨어는 1=왼쪽으로 가정. 거기에 두 모터 모두 +속도 = 뒤로.
- 해결: 펌웨어 `WHEEL_LEFT_ID 2` · `WHEEL_RIGHT_ID 1` → 재업로드, `robot.yaml` `left_dir: -1` · `right_dir: -1`.
- 교훈: **ID 먼저, 방향은 그다음** — 바퀴 하나씩 돌려 확인 ([OpenCR 문서 4장](../opencr/opencr-setup-ubuntu26.04.md)). 증상만 맞추는 부호 수정은 하지 말 것.
